# 실기기 UX 워크로드 분석

실제 Android 기기에서 앱을 조작하며 UFS 트레이스를 수집하고, 재현 가능한 워크로드
시나리오를 자산화한 결과를 정리한다.

- **측정 기기**: Samsung SM-S938N (Android 16, UFS)
- **측정 도구**: 본 agent (`--standalone`), UFS ftrace → Parquet → DuckDB 집계
- **측정 시기**: 2026-07-30 ~ 2026-08-16
- **저장 위치**: `~/.agent-standalone/agent.db` 의 `scenario_templates` (id 10~16)

---

## 1. 요약

앱마다 스토리지 I/O 특성이 뚜렷하게 다르며, **같은 시나리오도 캐시 상태에 따라
수 배에서 수백 배까지 달라진다**. 따라서 단일 측정값으로 앱을 특징짓는 것은 위험하고,
반복 측정과 조건 명시가 필수다.

핵심 발견 세 가지:

1. **실사용 앱 워크로드는 대부분 read 우위다.** 앱 실행 시 APK·리소스 read 가 사용자
   데이터 write 를 압도한다. 측정한 8건 중 콜드 상태에서 W/R > 1.0 인 경우는 없었다.
2. **예외는 카메라다.** 촬영 write 는 실제 파일 생성이라 회차와 무관하게 일정한 반면,
   앱 로딩 read 는 캐시되어 급감한다. 그 결과 워밍업 후 W/R 이 6배까지 올라간다.
3. **`completed` 는 "의미 있는 워크로드"를 뜻하지 않는다.** 모든 스텝이 성공해도
   실제로는 로딩 화면만 긁었거나 엉뚱한 페이지를 본 경우가 실제로 발생했다.

## 2. 시나리오별 I/O 프로파일

| id | 시나리오 | UFS 이벤트 | read | write | 특성 |
|----|----------|-----------|------|-------|------|
| 10 | 설정앱 탐색+검색 | 72K | 1.0 GB | 22 MB | **read 최다** |
| 11 | 크롬 위키 로드+스크롤 | 6.5K | 57 MB | 22 MB | 캐시 write |
| 12 | 유튜브 검색+피드 스크롤 | 9.7K | 93 MB | 18 MB | 미디어 버퍼링 |
| 13 | 갤러리 썸네일+사진 열람 | 약 1K | 1~4 MB | 3~7 MB | **경량 baseline** |
| 14 | 네이버 검색+피드 스크롤 | 9.4K | 95 MB | 28 MB | 혼합 |
| 15 | 앱 전환 반복 | 15.8K~51.9K | 94~677 MB | 78~184 MB | **read/write 균형, 변동 큼** |
| 16 | 카메라 사진 5장 촬영 | — | 4.6~139 MB | 27~37 MB | **유일한 write 우위** |

> **범위로 표기된 값(15, 16)은 반복 측정에서 실제로 변동한 폭이다.** 단일 값으로
> 인용하면 재현 시 불일치가 발생한다.

### 2.1 W/R 비 비교

콜드 상태(앱 캐시가 비어 있는 첫 실행) 기준:

| 시나리오 | read | write | W/R |
|----------|------|-------|-----|
| 설정앱 탐색 | 1024 MB | 22 MB | 0.02 |
| 유튜브 피드 | 93 MB | 18 MB | 0.19 |
| 카메라 사진 5장 | 139 MB | 31 MB | 0.22 |
| 네이버 검색 | 95 MB | 28 MB | 0.29 |
| 크롬 위키 | 57 MB | 22 MB | 0.39 |
| 앱 전환(평균) | 289 MB | 118 MB | 0.41 |
| 삼성노트 작성 | 147 MB | 65 MB | 0.44 |
| 카메라 동영상 30초 | 68 MB | 41 MB | 0.60 |

콜드 상태에서는 예외 없이 read 우위다.

### 2.2 카메라 — 워밍업에 따른 W/R 역전

같은 시나리오를 5회 연속 실행한 결과:

| 회차 | 1 | 2 | 3 | 4 | 5 |
|------|---|---|---|---|---|
| read | 139 MB | 57 MB | 18 MB | 4.6 MB | 19 MB |
| **write** | 31 MB | 37 MB | 36 MB | 29 MB | 27 MB |
| **W/R** | 0.22 | 0.65 | **1.97** | **6.29** | **1.40** |

write 는 27~37 MB 로 안정적이고 read 만 급감한다. **write 특성을 관찰하려면 1회
워밍업 후 측정해야 한다.**

## 3. 측정 방법론

### 3.1 자산화 기준

시나리오를 재사용 자산으로 등록하기 전 다음을 모두 통과해야 한다.

1. **3회 연속 실행 성공** — 1회 성공은 우연일 수 있다. 실제로 `clear_mode` 관련
   시나리오는 1회차 성공 / 2회차 실패 사례가 있었다.
2. **스텝별 `success=true` 확인** — raw output 을 직접 확인한다.
3. **trace 로 워크로드 유효성 확인** — 이벤트 수와 read/write 량이 의도한 수준인지.
4. **의도한 화면 도달 확인** — `dumpsys window | grep mCurrentFocus` 또는 UI 덤프로
   실제 화면 내용을 검증한다.

### 3.2 `completed` 를 신뢰하면 안 되는 이유

실제로 겪은 사례:

- **크롬 한글 URL** — 모든 스텝이 `success=true` 였으나 위키가 아니라 구글 검색
  결과 페이지를 스크롤하고 있었다. `adb input text` 로 한글 URL 을 입력하면
  검색어로 처리된다.
- **느린 페이지 로딩** — 해외 사이트(RTT 156ms)는 로딩에 8초 이상 걸리는데 5초만
  대기하면 로딩 중 화면을 스크롤하게 된다. 스텝은 전부 성공이지만 의미 없는 워크로드다.

### 3.3 변동성 판정 기준

반복 측정에서 값이 흔들릴 때, "재현 실패"와 "본질적으로 변동이 큰 워크로드"를
구분해야 한다.

- **재현 실패** — 어떤 회차에는 워크로드가 사실상 발생하지 않는다.
  (갤러리 heavy: 622 MB → 0.9 MB, 약 700배)
- **변동이 큰 워크로드** — 매 회차 상당한 I/O 가 확실히 발생하나 양이 흔들린다.
  (앱 전환: 최소 94 MB 보장, 2~3배 변동)

후자는 자산으로 유효하되 **분포로 해석**해야 하며, 설명에 변동 폭을 명시한다.

## 4. 실패 사례 (자산화하지 않은 것)

같은 곳에서 시간을 쓰지 않도록 기록한다.

### 4.1 갤러리 대용량 사진 (기각)

**시도**: Wikimedia Commons 고화질 사진 33장(715 MB)을 기기에 넣고,
`clear_mode="clear"` 로 썸네일 캐시를 매번 삭제해 대량 read 를 유발.

**결과**: 5회 측정에서 **622 / 35 / 622 / 0.9 / 6.3 MB** — 최대 700배 변동.
스텝은 5/5 성공했으나 어떤 회차에는 워크로드가 사실상 없었다.

**원인**: `pm clear` 는 갤러리 **앱 데이터**만 삭제하며, 썸네일 실체는 MediaProvider
쪽 공용 캐시에 남아 재사용된다. 앱 레벨에서 통제할 수 없다.

**교훈**: OS 캐시에 좌우되는 워크로드는 시나리오로 고정하기 어렵다. 재현 가능한
대용량 read 가 필요하면 `fio` 벤치마크 스텝이 적합하다.

### 4.2 삼성노트 작성 (기각)

**결과**: 1회차 성공, 2·3회차 실패.

**원인**: 1회차에 생성한 노트가 편집 화면(`ComposerActivity`)째로 복원되어 목록
화면의 "노트 작성" 버튼이 존재하지 않는다. 크롬 탭 복원과 동일한 유형.

수정 가능한 문제지만 3회 재현 기준을 통과하지 못해 등록하지 않았다.

### 4.3 카메라 동영상 녹화 (기각)

**결과**: 1/3 재현. 30초 녹화로 109 MB 파일 생성에 한 번 성공(W/R 0.60)했으나
이후 동영상 모드 전환이 실패했다.

**원인**: 카메라 모드 전환 UI 가 실행 시점 상태에 따라 달라져 `element_text="동영상"`
요소를 안정적으로 찾지 못한다.

### 4.4 진행하지 않은 것

- **넷플릭스** — 사용자 개인 계정에 로그인된 상태였다. 재생 시 시청 기록이 계정에
  남으므로 진행하지 않았다.
- **AnTuTu** — 합성 벤치마크는 실사용 앱 워크로드가 아니며, `fio` 스텝과 목적이 중복된다.

## 5. 앱 조작 함정 (실측)

### 5.1 상단 검색바 자동 숨김 — 유튜브, 네이버

스크롤하면 상단 바가 숨겨져 검색 요소를 찾을 수 없다. **검색 스텝을 스크롤보다
먼저 배치**해야 한다. 두 앱 모두 이것 때문에 1차 시도가 실패했다.

### 5.2 크롬

- **탭 복원** — `force_stop` 해도 이전 탭이 복원되므로 홈 화면이 아닐 수 있다.
  홈 상태에는 `search_box_text`, 페이지 로드 상태에는 `url_bar` 가 존재한다.
  **`url_bar` 쪽이 안전하다.**
- **한글 URL 불가** — `adb input text` 로 한글 URL 을 입력하면 검색어로 처리되어
  네비게이션이 일어나지 않는다. **ASCII URL 을 사용한다.**

### 5.3 네이버 — content-desc 접미사

`"검색어 또는 URL 입력, 버튼"` 처럼 `, 버튼` 접미사가 붙는다.
`element_match_mode="prefix"` 로 해결.

### 5.4 갤러리 — 동적 content-desc

사진 그리드 항목의 content-desc 가 실행마다 달라 요소 지정이 불가능하다.
좌표 탭(`tap`)을 사용한다.

### 5.5 1회성 시스템 다이얼로그

콜드 스타트 시 다음 팝업이 요소 탐색을 가로막는다. **한 번 닫으면 이후 재현에
영향이 없다.**

| 앱 | 다이얼로그 | 선택 |
|----|-----------|------|
| 크롬 | 알림 권한 | 나중에 |
| 크롬 | 기본 브라우저 설정 (`RequestRoleActivity`) | 취소 |
| 갤러리 | 위치 라벨 안내 배너 | 나중에 |
| 삼성노트 | 스타일 안내 툴팁 (`PopupWindow`) | 빈 곳 탭 |

> 삼성노트 툴팁은 `force_stop` 후 **매번** 재현되므로 시나리오에 닫기 스텝이 필요하다.

### 5.6 실패 원인 진단

`tap_element` 실패 시 에러 메시지에 현재 포커스 화면이 포함된다. 실패 3건 모두
이것으로 원인을 즉시 특정했다.

```
tap_element: 요소를 찾을 수 없습니다 (content_desc="검색")
  현재 화면: mCurrentFocus=Window{... com.google.android.permissioncontroller/
             com.android.permissioncontroller.role.ui.RequestRoleActivity}
```

포커스가 다른 앱이면 다이얼로그가 가린 것이고, 대상 앱 그대로면 요소가 숨겨진
것이다. **시나리오를 의심하기 전에 이 값을 먼저 확인한다.**

### 5.7 기타 환경 요인

- USB 와 무선 ADB 가 같은 기기를 2개 항목으로 노출한다. 무선은 임의로 끊길 수 있다
  (`adb connect <ip>:5555` 로 재연결).
- 화면이 잠기면 앱이 전면에 오지 않는다. `launch_app` 은 내부적으로 wake + unlock 을
  수행하지만, 수동 확인 시에는 직접 깨워야 한다.

## 6. 참고 데이터셋

### KAIST 스마트폰 앱/웹 사용 로그 (AI Hub #275)

- 피험자 33명 × 약 4주, 316만 이벤트, 2018년 10~11월 수집
- 라이선스 CC0, 약 1.1 GB (JSON)

**활용한 것 — 시간 구조**

앱 세션 길이 분포 (전체 11,015개 세션):

| p25 | p50 | p75 | p90 | p95 | 평균 |
|-----|-----|-----|-----|-----|------|
| 12s | **79s** | 197s | 298s | 413s | 130s |

중앙값 79초다. 현재 시나리오 5종이 2~3분이므로 p50~p75 구간에 해당하며,
실사용 기준으로는 오히려 긴 편이다.

또한 상위 앱 전환 패턴이 **3개 앱 왕복** 형태였고, 이를 근거로 시나리오 #15
(크롬↔유튜브↔설정 전환)를 설계했다.

**활용하지 않은 것 — 앱 목록**

상위 앱이 현재 환경과 맞지 않는다.

- 2위 `kaist.iclab.abc` (12%)는 **연구용 수집 앱 자체**로 실사용이 아니다.
- 3위 Fitbit(11%) 등 피험자 33명이 피트니스 앱 사용자에 편중되어 있다.
- 크롬·유튜브가 상위 30위에 없다.

표본이 작고 2018년 데이터라 앱 선정 근거로는 부적합하다고 판단했다.

### 최신 데이터셋 조사 결과

2024~2025년 공개 데이터셋을 조사했으나 목적에 맞는 것을 찾지 못했다.

- Kaggle 계열 스크린타임 데이터셋 — **합성(synthetic) 데이터**로 실제 로그가 아니다.
- 대규모 행동 로그(24,133명 / 5천만 이벤트, 2024) — 논문 부속 데이터로 공개 조건이
  불확실하고, 행동 단위가 생활 범주라 앱 단위 변환이 어렵다.

모바일 앱 사용 로그는 개인정보 성격이 강해 공개가 어렵고, 최신일수록 합성이거나
접근이 제한된다. 직접 수집이 현실적인 경로다.

## 7. 한계

- **단일 기기 측정** — SM-S938N 1대 기준이며, 기기·Android 버전·저장장치 세대에 따라
  수치가 달라질 수 있다.
- **캐시 상태 미통제** — 대부분의 측정에서 OS 페이지 캐시·앱 캐시 상태를 통제하지
  않았다. 회차 간 변동의 상당 부분이 여기서 온다.
- **충전 상태·온도 미기록** — 발열에 의한 thermal throttling 이 스토리지 성능에
  영향을 줄 수 있으나 기록하지 않았다. 향후 각 시나리오에 배터리·온도 기록 스텝
  추가를 검토한다.
- **표본 수 부족** — 대부분 3회, 일부만 5회 측정이다. 변동이 큰 시나리오는 분포를
  논하기에 표본이 부족하다.

## 8. 재현 방법

```bash
# agent 기동 (standalone, 영속 DB 사용 — HOME 을 변경하지 말 것)
./agent --standalone -config config/devices.toml

# 시나리오 실행
curl -X POST http://127.0.0.1:50051/api/agent/scenario/run \
  -H 'Content-Type: application/json' \
  -d '{"deviceIds":["<deviceId>"],"scenarioName":"<name>","steps":[...]}'

# 상태 조회
curl "http://127.0.0.1:50051/api/agent/benchmark/status?jobId=<jobId>"

# trace 통계 (raw output 의 TRACE_STOP 줄에서 job_id 추출)
curl -X POST http://127.0.0.1:50051/api/agent/trace/result \
  -H 'Content-Type: application/json' \
  -d '{"jobIds":["<traceJobId>"],"filter":{}}'
```

> **주의**: `HOME` 을 임시 디렉토리로 지정해 agent 를 실행하면 SQLite DB 가 그 안에
> 생성되어 저장한 시나리오가 소실된다. 영속 저장에는 기본 `$HOME` 을 사용한다.

저장된 시나리오는 UI 의 Scenario 탭 상단 드롭다운에서 선택해 바로 실행할 수 있다.
